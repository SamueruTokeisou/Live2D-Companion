# AI 虚拟主播项目企划书

版本：2.0。更新：2026-11-24。项目：Live2D Companion。所有者：SamueruTokeisou。

这是当前产品与实施主线，替代1.x版的桌宠阶段顺序。代码版本仍为0.4.3-dev；修改企划不等于实现新功能。P1–P8旧编号保留在历史验收记录，后续按本书R0–R6交付。

## 1. 我们要做什么

做一个能在直播间工作的单角色AI虚拟主播：听见或读到观众发言，知道正在和谁说话，给出自然回应，用声音、字幕和动作表现出来；能切换聊天与唱歌，记住本场发生的事情，为持续支持者建立独立观众档案。桌宠是它的日常运行方式，直播才是产品主线。

近期先服务一位主播、一个直播平台、一个角色和一台现有电脑。角色身体可以替换；不把多角色同台作为第一版前置条件。先让真实观众能看、能聊，再扩展商业产品常见的运营能力。

执行原则：成熟项目有合适实现就优先复用，成熟软件能承担的职责就通过接口接入。我们重点建设直播调度、观众识别、记忆边界、表演控制和运营体验。公开代码不是无条件可复制；复用时固定版本、保留署名，逐项核对代码、前端、模型和素材的许可。

## 3. 产品模式与明确取舍

- 桌面模式：继续普通中文AI对话，不强制动漫角色人格；外观和音色不决定性格。
- 直播模式：补充最低必要的场景认知，包括主播身份、直播状态、观众昵称、正在进行的节目、已提供的工具和当场上下文。没有执行过的动作不能声称已执行。
- 所有者可配置称呼、禁忌话题、回应长度和节目口吻；首期不开发人格自主改写、复杂心理数值或多Agent自治。
- 记忆重新进入主线：这是所有者2026-11-24的新决定，替代“暂不做长期记忆”的旧产品选择。先做本场记忆，再做按观众隔离的长期档案。
- 功能目标可以积极，失败处理必须具体：每个会发声、写记忆、发起外部动作的功能都要有停止、回执和人工接管。

## 4. 第一场演示应该是什么样

所有者打开控制台，选角色和声音，点击“进入演示”。OBS能看到干净的角色画面与字幕，听到独立角色音轨。观众发来消息，主播挑选一条回应，能叫对昵称，字幕与声音一致，嘴部开合。重复弹幕不会把队列堵死。

所有者可以随时点“停止说话”“暂停互动”或按紧急静音快捷键。聊天能切到一首已准备歌曲，再切回聊天；早期这是歌曲播放通路，不能宣传成实时歌声生成。演示结束后得到简洁的事件、用量和故障回顾。

这是R1的第一条完整使用链。它不等待完整身体工作台、所有平台接入或完整商业运营系统。

## 8. 直播事件与发言调度

统一事件携带platform、roomId、viewerId、eventId、发生时间、类型和文本。显示昵称可以变化，身份不能只靠昵称。重复投递按eventId去重，恢复连接不得重放礼物权益或感谢。

首期优先级：所有者紧急控制→人工点名回应→需要及时处理的节目控制→支持者互动→普通弹幕→闲聊。支持者可以更快被选中，但每段时间预留普通观众机会；优先级不等于每条礼物都打断歌曲。

初始策略为小队列、短回答、重复弹幕合并、礼物感谢合批和冷却。爆量时选话题/抽样回应，不尝试把所有弹幕都交给大模型。排队过久的闲聊过期，旧消息不在数分钟后突然被读出来。具体队列长度、冷却和发声频率在回放数据中调整。

当前每分钟6轮、单进程24轮是桌面试验限制，不适合直接用作直播运营。R1/R2改为可配置的小时/当日请求与费用预算，不能靠反复重启重置额度；已有后端不可用时能停互动并交给所有者。

## 9. 当日记忆与支持者独立文件

### 当场/当日记忆

每场直播有sessionId和明确开始/结束时间，采用配置的时区；跨午夜仍能知道属于哪场，不简单依赖系统日期切文件。当前主题、近期对话、已讲过的笑点/节目结果和观众临时事实分开记录。

设计默认值：原始短期记录保留24小时、当场小结保留7天，均可由所有者修改；自动过期和手动清空都必须覆盖摘要索引。不是永久保存所有弹幕。没有长期档案授权的临时事实不自动升级为永久记忆。

### 观众长期档案

独立路径计划为private/viewers/<platform>/<roomId>/<viewerId>/，包含profile.json、memories.jsonl和变更记录；当场事件可用SQLite作索引，观众事实仍能导出为独立文件。这里的private是目标私有数据根，实际实现放在Git忽略目录下，不创建公开观众文件。

目录名由规范化身份派生，不直接拼接昵称或未经检查的路径；写入仍校验目录包含关系。长期档案初始保留期建议30天，可配置更长，并提供清晰的用途和退出方式。每条记忆包含主体UID、来源eventId/sessionId、记录时间、状态、保留期限与用途。昵称不是唯一键，平台ID不同不能合并。更换身体仍检索同一观众，不能把角色档当观众档。

“老板独立记忆”具体做成支持者档案：按可信礼物/会员事件或所有者人工登记开启，记住希望的称呼、明确表达的偏好、上次互动话题及节目约定。可以按权益配置容量、保留时间和互动优先级；不把支付金额直接塞进对话提示，也不让模型根据一句“我刷了很多”授予权限。

不记录付款凭证、联系方式或推断的敏感个人标签；账单/权益与聊天事实分开。观众应能获知记忆用途，并有可操作的查看、修改、忘记和退出路径；观众请求先验证身份或交给所有者处理，不能让另一条弹幕清掉别人的档案。删除后的事实不能从旧摘要、缓存或备份自动复活，恢复备份时也遵守删除标记。

普通观众至少有本场记忆，支持者可有更持久的服务。模型使用实际可提供的权益，不把付费排名换算成虚构的亲密度；私人档案只检索当前回应所需的内容，不向其他观众公开。

## 10. 唱歌路线

分三层做，不把TTS强行当歌声模型：

1. 播放层：歌单、请求者、队列、伴奏/人声、音量、切换、停止和回到聊天。先用准备好的音频把节目跑通。
2. 制作层：离线制作歌声，可评估RVC等音色转换方案；基础人声、旋律、歌词及声音素材分别记录来源。预处理歌曲后直播时只播放，避免8GB显存同时承担OBS、TTS和歌声训练。
3. 表现层：歌曲时间轴驱动字幕/口型/动作，支持主持串场和结束感谢。歌词展示只使用有相应使用依据的内容；首版可以只显示歌名和进度。

第一版曲库目标3–5首，选择可准备、可试听的范围。热门歌的即时任意生成、任何声优音色和无限曲库不是第一版承诺。歌声不必绑死当前说话参考，日后可换成自己的原创声音。

## 11. 搜索、节目与扩展能力

先增加只读搜索、天气和资料查询，结果带来源和时间。观众消息、检索页面和歌词内容都是输入数据，不是所有者指令。工具执行采用允许列表、参数校验、超时和每轮调用上限；观众不能让主播执行任意代码、访问本机文件或更改直播凭据。

后续节目包括话题投票、点名问答、知识互动、合作游戏、观众投稿和定时节目。屏幕理解与游戏操作分别立项，先有可停止的独立演示，再进入直播。多角色同台、插件市场和跨平台同步可以继续评估，但不占用第一场直播的关键路径。

## 12. 技术分工与复用路线

| 责任 | 默认路线 | 复用方式与边界 |
| --- | --- | --- |
| 角色渲染 | 保留现有Electron/Pixi/Cubism舞台 | 不从零重写渲染器；大肥鱼与generic逐步成为显式身体适配器 |
| 主播内核 | JS/TypeScript共享核心 | 新业务独立模块，先定义边界，再分离现有文件；不做一次性大搬家 |
| 管理界面 | 逐步并入统一Electron控制台 | Tkinter管理器进入维护模式，不再扩张为第二套主播控制台 |
| 对话/搜索 | 保留后端适配，工具与账号相互独立 | 新增服务先核对授权与额度；本机账号登录不等于无限公众服务 |
| 语音/歌声/识别 | Python独立工作进程 | 通过受控本地接口使用，按需加载；优先复用成熟推理服务，不重写模型算法 |
| 观众接入 | 官方平台通路优先 | 默认首个平台候选B站，最终按所有者直播平台确定；拿不到权限时继续回放开发，不绕过访问控制 |
| 推流与音轨 | OBS及其控制接口 | OBS负责推流；项目负责输出、状态与节目控制，推流密钥不进模型或仓库 |
| 存储 | SQLite索引+可导出的观众文件 | 先不用向量库；检索不足后按数据量评估 |

源码目录演进目标：上游只读快照、补丁或差异清单、自有companion模块、平台适配器、语音服务和测试分开。现有source/desktop-v1.1.0仍是实际维护入口，移动前先使安装器、导入路径、回归与打包同时适配；本次只改规划，不让文档声称目标目录已经存在。

依赖复用登记到一张清单：组件、固定修订、实际文件、用途、许可、权重/素材条件、修改内容和替换方案。不能把GPL/AGPL或附加商用条件的组件直接并入后继续把所有内容统称MIT；独立进程也不自动免除许可义务。

## 13. 公开展示最低条件与后续质量

必须先解决：固定控制令牌、控制服务来源/主机校验、静态目录边界、过宽RPC、日志/模型/声音素材泄漏、无法停止发声、不同观众记忆串用。R0建立对应回归，未通过不进行公开无人值守直播。

本轮代码核对仍见main.mjs的local-app及server默认dev-token，并见静态路径startsWith检查；列为已确认需要整改的实现，不把审稿中的任意代码执行推断当成已复现漏洞。

源代码构建分步推进：R0盘点并固定依赖与专有组件来源，R1形成可重复开发启动和构建流程，R6达到可追溯发布产物、安装回归及升级回滚。现有“固定上游运行包+覆盖自有JS”仍是过渡安装路径，不伪称已有源码独立重建能力。

多屏、不同DPI和休眠列入环境覆盖清单；缺设备不阻塞本机演示，不能用“未覆盖”掩盖已经复现的故障。当前内存增长继续跟踪，公开长时开播前要完成新直播链资源采样和已知问题的处置，不借用旧8小时结果替代新测试。

## 14. 成本与资源策略

使用现有RTX4060笔记本与8GB显存作为首个环境。展示、TTS、OBS及歌声制作共享资源，优先预生成歌曲、按需加载模型、限制回答长度；不在直播同时训练声音或堆叠多个大模型。

新增云端支出默认不启用。需要付费接口时先给出供应商、实际价格依据、单次/每小时/每日上限和小额试播预算供所有者选择。月度预算是配置，不是开源项目保证免费；不能把Plus订阅当作所有语音、搜索和公众场景都已包含。

记录实际请求、已知token、语音时长和本机资源；缺少价格时保留未知，不能虚报金额。接近限额时减少闲聊/合并感谢，达到硬限额暂停云端请求并通知所有者，不自动充值或换付费账号。

接受“先做可见闭环、源码边界清楚、安全先收口、复用成熟实现、统一最终界面”的建议，分别落在A01–A08。
