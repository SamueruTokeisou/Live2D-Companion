# 单角色伙伴内核项目企划书

版本：1.0。制定日期：2026-11-22。项目：Live2D Companion。

执行依据：以本企划为当前开发主线；ROADMAP 是摘要，Ideas 是未承诺的候选。P1 已开始实施，当前进度见 [P1 实施与验收](P1_FOUNDATION.md)。本企划中的后续能力不代表已实现。

## 一 项目目标

做一个能长期陪伴用户、可以更换身体的单角色伙伴内核。先用现有 Live2D 模型验证体验，未来可以接入 3D 或其他形象。人格、记忆、对话和事件调度应独立于具体模型。

项目首先服务于零基础、预算有限、希望逐步制作自己角色的个人用户。基础桌宠离线可用，AI 与声音按阶段增加。先让一个角色回应可靠、状态清楚、能被打断，再增加表现与玩法。

项目负责人负责需求拆解、技术方案、迭代排序、实现、验证和交接。SamueruTokeisou 是项目所有者和体验验收者，保留产品方向与发布决定。日常技术细节和可逆实现由负责人推进；涉及新增付费支出、素材授权或重大数据处理范围变化时，先明确具体方案与影响。

## 三 产品与技术原则

1. **内核优先。** 身体负责表现，内核负责状态、对话、记忆、调度和恢复。
2. **单角色优先。** 允许替换身体，不开发多角色同台或多伙伴编排。
3. **先闭合流程。** 一个需求必须有输入、处理、结果、取消与失败处理。
4. **离线基础可用。** 待机、点击反馈、普通提醒和计时由本地逻辑处理。
5. **用户能控制。** 能暂停、打断、免打扰、查看记忆、清空记录并退出。
6. **证据决定完成。** 语法通过、接口成功、画面正常、长期稳定分别验收。
7. **渐进改造。** 保留现有可用程序，通过接口逐步接入新内核，不一次性推倒重写。
8. **免费优先。** 先使用现有电脑，依赖按必要性引入，云端服务可选。

## 四 总体结构

输入事件进入队列，由内核决定处理顺序；必要时调用模型；工具执行器校验请求后，把语义动作交给身体适配器；结果和必要状态保存在本地。

| 部分 | 首期责任 | 边界 |
| --- | --- | --- |
| 输入与事件队列 | 接收文字、点击和计时事件；合并小事件；处理优先级 | 不要求每次点击都调用模型 |
| 状态机与任务调度 | 待机、思考、回应、暂停、出错；任务取消与超时 | 同时只维护一个主对话任务 |
| 对话后端接口 | 请求、流式输出、取消、用量和错误归一化 | 先验证一个真实后端，再扩展 |
| 人格与记忆 | 固定人格、已确认偏好、近期对话、记忆候选 | 人格和长期事实分开，保留变更记录 |
| 工具与身体接口 | 查询能力；说话、表情、视线、手势、停止 | 不把模型返回值直接当代码执行 |
| 持久化与诊断 | 本地设置、事件摘要、任务结果、用量和脱敏诊断 | 不公开模型、密钥、私人聊天或控制口令 |

拟采用 Node/TypeScript 承载新内核，与现有 Electron 舞台建立明确消息接口。Python 管理器暂时保留，是否统一界面在实际维护成本明确后决定。具体依赖在对应阶段核对许可、兼容性和维护状态。

### 身体契约

首批语义能力包括：查询能力、显示文字、设置情绪、指定视线、播放手势、停止当前表演。每条指令有任务编号，返回受理、完成、取消、失败或不支持。

Live2D 与未来 3D 适配器各自把语义指令转换为模型参数或动画。不支持的动作明确返回，不假装执行。换身体保留人格与已确认记忆；窗口位置、缩放和参数映射仍属于身体配置。

## 六 阶段验收门槛

### G1 运行地基

- 在隔离目录完成安装、导入和启动；不得依赖维护者本机绝对路径或隐藏配置。
- 重复打开管理器能定位已有实例；连续点击启动不会产生冲突实例。
- 导入先检查再处理，使用临时目录；失败不注册角色、不覆盖原件和已有角色，取消后能恢复可用状态。
- 配置带版本，采用原子写入和备份；损坏时给出明确恢复路径，升级不得静默清空用户数据。
- 正常退出能收起进程和资源，再启动能恢复所选角色与必要设置。
- 完成 30 分钟和 8 小时采样，以及本机可用条件下的 DPI、多屏和休眠唤醒检查。缺少设备的组合明确记为未覆盖。
- 记录 CPU、内存、帧循环与故障摘要。先形成可复现基线，再制定性能阈值；不凭空承诺具体占用。
- 阻断安装、正常使用、退出或导致数据损坏的问题清零，才能进入下一阶段。

### G2 最小事件内核

- 用户文字、点击、计时事件进入统一队列；有事件编号、来源、时间、任务归属和结果记录。
- 连续小事件合并；免打扰时遵守策略；用户输入优先于待机行为。
- 状态转换可观察，异常不会永远停在“思考中”。
- 任务取消覆盖排队、执行中和迟到结果；旧任务取消后不得重新冒字幕或恢复旧动作。
- 模拟对话后端只用于工程测试，界面明确区分；不宣称已经接入真实 AI。
- 用确定性测试覆盖合批、优先级、暂停、取消、超时、失败和恢复。

### G3 文字对话

- 至少连接一个真实后端完成多轮中文交流；真实后端可为本地模型或用户明确选择的服务。
- 有请求超时、最大输出、每轮调用上限、有限重试和用户可见的错误状态。
- 用户可以停止当前回应并开始新一句；旧请求的迟到结果被丢弃。
- 角色只调用已登记能力，参数经过类型、存在性和范围校验。
- 模型服务不可用时，桌宠显示和本地互动仍可使用。
- 记录可取得的 token 用量和调用次数；缺少计费信息时标注估算或未知，不显示虚构金额。
- 没有完成真实后端验证时，保留该阶段为未完成。

### G4 可控记忆

- 人格说明、用户确认的偏好、近期对话和事件日志分别存储。
- 首期仅通过用户明确操作或确认后的候选写入长期事实；模型不任意改写人格与用户档案。
- 每条长期记忆带来源、时间与状态；修改有历史，可导出、删除或撤销。
- 用户删除的信息不得在重启或上下文重建后从旧摘要自动恢复。
- 新会话只带必要人格、近期上下文和相关记忆；普通情绪反馈不触发额外记忆模型调用。

### G5 声音链

- 先完成可替换的语音输出，再接按键说话的语音输入；默认不常开收音。
- 字幕、声音和口型共享任务与时间依据；暂停、结束和打断同步处理。
- 先以音量包络验证嘴部开合；更精细的口型在模型和语音数据支持后另行评估。
- 语音服务停止或初始化失败时能回到文字模式；不让舞台崩溃。
- 测量冷启动、热启动和打断延迟，再制定体验目标，不套用外部项目数字。

### G6 身体工作台

- 可映射眼睛、嘴、视线、转头和呼吸，校准方向、范围与增益，即时预览。
- 明确区分穿戴/体型等保持状态与临时表情；临时表情结束不误清理穿戴。
- 大肥鱼专属行为逐步迁入明确适配层，既有功能保持可回归。
- 角色档带版本，可导入导出，只分享配置与动作，不携带第三方素材。
- 至少三套有权使用的模型完成实际验证，缺参数能解释并降级。
- 用测试适配器验证更换身体不影响人格与记忆。真实 3D 接入单独评估，未实现前不宣传 3D 可用。

### G7 单角色陪伴

- 番茄钟、简单提醒与动作配方在断网时可用；不因为每次点击而请求模型。
- 活泼程度、动作幅度、主动说话频率独立可调，并有免打扰开关。
- 重复事件有冷却和合并，避免连续提醒；全屏或会议策略由用户控制。
- 用户可以保存、预览和撤销自己的配方；不使用惩罚式亲密度和连续登录压力。

### G8 整体发布

完成从获取程序、导入模型、设置偏好、对话、打断、重启、升级到恢复备份的完整流程。重新审查依赖与素材许可、发布内容和数据迁移；完成安装与长时回归后，才将该版本标为正式稳定版。

## 八 预算与复杂度控制

| 项目 | 首期策略 |
| --- | --- |
| 硬件 | 使用现有电脑，不以购买新硬件为启动条件 |
| 模型、绘画与身体 | 继续使用已有合法素材；原创角色制作作为独立学习线，不阻塞内核 |
| 对话 | 先验证一个后端；本地模型按中文效果、响应和资源实测后选择；云服务由用户选配 |
| 调用次数 | 待机/点击/计时走本地规则；只在需要语言理解时调用 |
| 上下文 | 限制近期内容，按需附带记忆；摘要整理设置明确触发条件和次数上限 |
| 存储 | 首期使用结构化配置、追加事件日志和可读记忆文件；出现实际查询瓶颈后再评估数据库 |
| 语音 | 先评估系统已有声音和可用本地方案；引入模型前核对授权、体积和资源 |
| 工程依赖 | 不建设多 Agent、插件市场和分布式服务；先维护单个主对话流程 |

不承诺“开源就永久免费”“本地模型一定流畅”或未经实测的月费用。负责人在引入收费服务前给出调用方式、可设置的限制与费用依据。

## 九 暂不实施范围

多角色同台、多伙伴自主协作、手机与多平台同步开发、完整 3D 工作流、自研渲染引擎、插件市场、常驻看屏幕、自动操作电脑、向量记忆系统与人格自主改写，均不进入近期开发。

Coopanion/Cortico 与棉花糖保留为设计参考。新内核按自身需求实现；如以后复用其代码，先核对对应许可，不能把不同授权直接合并后继续标成纯 MIT。

## 十 维护与交付方式

负责人在当前授权工作中推进常规技术决策，不把每个实现细节都交回零基础用户。用户主要参与体验反馈：是否自然、是否打扰、哪里看不懂、希望它如何回应。

每轮交付包含：本轮变化、具体使用方法、测试结果、未解决问题、下一项任务。功能分支保留清楚提交，小步合并；发布前完成相应验收和回滚准备。

文档职责：本企划管阶段与完成标准；ROADMAP 管进度摘要；Issue 管具体任务；VALIDATION 管已发生的测试事实；Ideas 管未选入的构想。已有 Issue 的旧版本号仅保留历史含义，更新任务时需映射到 P 阶段，不能与新主线并行扩张范围。

新想法先记录，不自动进入当前迭代。只有写清使用过程、依赖和完成标准后，才由负责人安排进入阶段。

## 十一 完成后的用户体验

用户启动一个角色，能够看懂它的状态；说话时得到回应，随时可以打断；认可的信息才进入长期记忆。换成自己的新模型后，伙伴的名字、性格与已确认偏好继续保留。断网或模型服务故障时，它仍能作为基础桌宠使用，并清楚告诉用户发生了什么。

当前正式决定：先完成 P1 的运行地基，再做 P2 的最小事件内核。按验收推进，逐步形成真正可维护的伙伴系统。
