# 维护约定

SamueruTokeisou 是项目所有者和体验验收者。项目负责人在工作会话中承担需求拆解、技术方案、迭代排序、实现、验证和交接，常规技术细节自主推进；项目所有者保留产品方向与发布决定。

当前实施依据为 [项目企划书](PROJECT_PLAN.md)，阶段验收通过后再前进。当前 P1 已授权执行，正在实施与采样；没有建立周期性自动化。长测结果未审查前不进入 P2。

## 每轮开发

1. 先读 PROJECT_PLAN、README、ROADMAP、AGENTS 和当前问题记录。
2. 把需求写成一个可观察的使用过程，说明本轮交付和不确定点。
3. 优先修基础可用性，再增加玩法；一般改动在功能分支完成。
4. 做与变更相关的测试。窗口、GPU、音频、休眠等行为需要实际环境证据。
5. 汇报变化、测试结果、限制和下一步；同步文档，避免只把知识留在聊天记录。

## 版本节奏

不承诺固定日历工期。每个小版本聚焦一个主题：稳定、角色适配、玩法、声音等。满足验收条件再发版；开发基线不包装成正式稳定版。

每周使用者可以记录一次“哪里好玩、哪里打扰、哪里看不懂”。这是一种人工维护建议，不是已创建的定时任务。

## 决策原则

- 基础能力可离线，云端服务可选，费用事先说明。
- 用户有暂停、免打扰、清空记录和退出的能力。
- 不发布用户模型、密钥、私密日志或未确认授权的声音素材。
- 引入外部代码先核对许可；保留上游署名与修改边界。
- 不重写已经可用的部分，只为明确问题调整架构。
- 新想法先放 Ideas；被选中后补验收，再进入 Roadmap。

## 后续会话的入口

给 AI 的一句话示例：“继续维护 Live2D-Companion，先读项目企划书，从当前 P1 运行地基的下一项任务开始。”

角色档、代码与维护记录在仓库中传递；公开仓库不会保存私人聊天和完整模型。需要自动化巡检或定时维护时另行明确任务和频率。
