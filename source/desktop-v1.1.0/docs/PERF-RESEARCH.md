# 桌宠性能：开源项目与官方文档调研（2026-11-04）

> 背景：`docs/SPEC.md` §11.4 记录的二轮渲染层优化已全部回滚。本文是回滚后重新调研的结论，
> 目的是确认「已有项目踩过哪些坑」「哪些经验可复用」「哪些路不要再走」。

## 0. 一句话结论

已有的 Live2D 桌宠项目里**没有人靠「渲染状态缓存 / 网格缓存」这类做法拿到效果**；
社区真正有效的经验集中在三处：**掩码预处理（官方，桌面端收益小）**、**帧预算分档 + 按需唤醒**、
**帧节奏对齐刷新网格**。我们上一轮的方向没有先例，这也解释了它为什么测不出收益。

## 1. 官方：Cubism SDK 掩码预处理

- [Mask Preprocessing Methods (Native)](https://docs.live2d.com/en/cubism-sdk-manual/ow-sdk-mask-premake/)
- [Mask pretreatment methods (Web)](https://docs.live2d.com/en/cubism-sdk-manual/ow-sdk-mask-premake-web/)

做法：所有 mask 在模型绘制开始**一次性**画进 1 张 mask buffer，靠 RGBA 四通道 + 2/4/9 分割最多容纳 36 个 mask；
取代「每个需要裁剪的 drawable 各画一次 mask」的通用法。官方给出的收益来源是
**RenderTarget 切换 + Clear 的次数**（移动端这两条指令比普通指令贵得多）。

官方 Windows PC 实测（Haru 单模型，各环节耗时，同量纲）：

| 环节 | Windows PC | Android1 |
| --- | --- | --- |
| 掩码生成（L2MaskMake） | 318.5 | 2686.8 |
| 其余绘制（L2draw） | 1217.0 | 4004.1 |
| 整模型渲染（L3rendering） | 1892.0 | 6715.7 |

即**桌面端掩码只占整模型渲染约 17%**，绝对值也在几十到一百多微秒乘十的量级——
在 4070 这种机器上不是大头。同一页还给了「动态调整 mask buffer 尺寸」的旋钮
（默认 256×256，越大越清晰越慢），以及 `UseHighPrecisionMask(true)` 这个**更慢**的质量档，
说明官方的默认路线本来就是预处理。

**对我们的意义**：`untitled-pixi-live2d-engine` 走的是 native Cubism Core，掩码管理在核心里，
既够不到 `SetClippingMaskBufferSize`，也切不了预处理/高精度双档。这条路**在我们这套技术栈上根本不可达**，
而按官方数据就算可达，PC 上的天花板也就 1ms 量级。

## 2. 「锁帧」的坑：社区实测推翻了我的直觉

[Three ceilings a character runs into](https://saytu.ai/blog/three-ceilings-a-character-runs-into)

作者在 120Hz 屏上给 Pixi ticker 设了 `maxFPS = 60`，结果**观感变差**：

> 节流的实现是跳过 rAF 回调，而 rAF 按显示器自己的节奏到达。
> 在 120Hz 上请求 60 并不会得到均匀的 60，而是量化到 120Hz 边界的「留住/丢掉」模式，
> 于是转头动作读起来是 judder，而不是「更低的帧率」。

他们的结论是：**不加帧率上限**，省下来的性能从降分辨率（clamp DPR ≤ 2）等处拿——「一帧更便宜，好过一帧被跳过」。

**对我们的意义**：我此前建议「锁 60/120 或开 vsync」是不严谨的。
真正的判据不是「锁不锁」，而是**目标间隔必须是刷新周期的整数倍**，
且**不能靠 rAF 跳过来实现**（否则跳哪一帧由系统决定，节奏不齐）。

## 3. 帧预算分档 + 按需唤醒（HarmonyOS Live2D 桌宠实战）

[HarmonyOS NEXT 开发实战：给常驻 Live2D 桌宠"降速"](https://developer.huawei.com/consumer/cn/blog/topic/03225758628202176)

NekoBuddy 的三层机制，以及几条能直接搬的语义：

| 场景 | 帧预算 | 备注 |
| --- | --- | --- |
| 交互 / 用户触发动作 / 说话 | 16ms | 只有**用户**触发的才算 |
| 自动 idle 动作 | 33ms | 「自动 idle ≠ 用户交互」是最常见的耗电根源 |
| 程序化静置 | 60ms | |
| 睡深 ≥ 0.55 | 120ms | |
| 睡深 ≥ 0.75 | 240ms | 静置电流 500–600mA → 4fps 档 |

可复用的四条：

1. **帧预算写成纯函数**，好单测、好调档。
2. **对齐刷新网格**：`目标间隔` 向上取整到 `实测周期` 的整数倍。
   他们的原话——否则「60/120/240ms 的慢档在高刷屏上会错误退化成约 30fps」。
3. **低帧率不能丢时间**：两帧之间真实过去 250ms，动作 elapsed 要如实累计，
   否则动作忽快忽慢；长中断后的视觉跳变另走「视觉时基重置」。
4. **热封顶只能更慢不能更快**（与自适应值取 max，不是替换）。

**对我们的意义**：第 2 条直接命中我们的观测——窗口帧间隔实测 **17.7ms / 35ms 交替**。
这两个数如果正好是刷新周期的 **1 倍 / 2 倍**，就说明帧耗时**卡在 deadline 上**：
一帧刚好挤进一个周期，下一帧就滑到两个周期。判据很简单：拿实测周期去除这两个间隔。

## 4. Electron 桌宠的四个真实坑

[给桌面养了个鸣潮桌宠，在旧笔记本上卡成了PPT](https://jishuzhan.net/article/2086842146727804929)

| 坑 | 做法 | 我们的现状 |
| --- | --- | --- |
| 主线程硬抠 233 万像素（1–3s 卡死） | 搬 Web Worker + Transferable 零拷贝 + 结果按路径缓存 | ✅ 我们只在低频事件读像素，且已改成只读包围盒 |
| `willReadFrequently: true` 用在「每帧被 drawImage 的源」canvas 上 | 该 flag 把 canvas 钉死在 CPU 软件后端，「硬件加速名存实亡」 | ✅ 全仓无此 flag（已 grep 核对） |
| `shadowBlur` 的强度用指数逼近，永远到不了 0 | 常驻一个几乎看不见的高斯模糊 | ✅ 无此逻辑 |
| 空闲隔帧渲染到 30fps | **跳帧的前提是不清屏**——透明无边框窗口不保证保留上一帧内容，一清屏就闪白 | ⬜ 未做；若做必须同时关掉 `clearBeforeRender` |

他们的实测：Worker + 缓存后总耗时 118ms（含解码），主线程最大阻塞 28ms。

## 6. 物理帧率与「脸抖」

- [Live2D Editor 手册 · 物理运算](https://docs.live2d.com/ko/cubism-editor-manual/physics-operation/)：
  物理「计算 FPS」默认 **60**，用途未定推荐 60。
- [VTube Studio 帧率排障文档](https://docs.glycoproduction.com/zh-Hans/docs/troubleshoot/fps/)：
  「若物理突然**抖动**或发黏，请确认帧率设置未被改变」，推荐 App FPS 60、
  且 **physics Frame rate = Match Application FPS**。

也就是说，脸部这类由物理驱动的细节，**对帧步进不齐最敏感**：
物理按 60fps 的基准算，渲染却在一个 17.7/35ms 交替的节奏里出帧，参数曲线就会一顿一顿。
这与我们观察到的「概率性脸抖、状态无关」一致，也解释了为什么拆掉渲染层缓存毫无改善。

## 7. 官方与第三方应用的做法对照

- [Live2DViewerEX FAQ](https://github.com/alipymanbu/Android/blob/master/官网版APP下载/live2dviewerex/常见问题与故障排查.md)：
  渲染出问题时官方建议把「帧率」改成 **垂直同步**；手机桌面端模型帧率封顶 60
  （APP 内自定义 120FPS 只对 APP 内有效）。
- 结论指向同一处：**让出帧节奏跟显示器对齐**，而不是让应用自己随机出帧。

## 8. 实测（2026-11-04，本机：RTX 4070 Laptop / 2560×1440 @ 240Hz / 窗口 457×837）

工具：`tools/lab/cadence.mjs`（帧间隔 + 折算成刷新周期）、`tmp/rafonly.mjs`（停掉 ticker 后测合器 rAF 空转节奏）、
`tmp/worktime.mjs`（单帧 update+render 耗时）。

### 8.1 合成器给这个窗口的网格

| 条件 | 空转 rAF 间隔 | 折算 |
| --- | --- | --- |
| 解码 vsync（`disable-gpu-vsync` + `disable-frame-rate-limit`） | 0.5ms 连发，另有一簇 17.5ms | 与显示完全脱钩 |
| 恢复 vsync（`STAGE_VSYNC=1`） | **4.17ms**，p10–p90 = 4.1–4.3 | **1.01 拍，干净的 240Hz 网格** |

结论：**网格本来就在，是被那两个开关解掉的**。240Hz 下 1 拍 = 4.167ms，
可用的均匀节奏只有 240/k：120(2 拍) / 80(3 拍) / 60(4 拍) / 48(5 拍)。

### 8.2 单帧工作量 vs 拍边界

| 条件 | 均值 | p10 | 中位 | p90 | max | 落在 12.5ms 之上/之下 |
| --- | --- | --- | --- | --- | --- | --- |
| 打包版 解码 vsync | 14.86 | 13.6 | 14.7 | 16.1 | 17.3 | 80 / 0 |
| 打包版 恢复 vsync | **12.83** | 11.7 | 12.7 | 14.1 | 15.4 | **50 / 30** |

`12.5ms` 是 3 拍（80fps）的边界。**工作量正好跨在这条线上**：
一半帧挤得进 3 拍，一半挤不进掉到 4 拍 → 屏幕上前一帧停 3 个刷新、后一帧停 4 个，随机交替 —— 这就是「概率性抖动、且与状态无关」的来源。

### 8.3 帧间隔（生产节奏）

| 条件 | 均值 | p10 | p90 | 折算拍数 |
| --- | --- | --- | --- | --- |
| 解码 vsync，不限帧 | 13.12 | 11.5 | 14.1 | 2.6 ~ 4.6，浮在网格外 |
| 解码 vsync，限 60 | 18.11 | 13.1 | 31.7 | **3.4 / 7.7 交替，最差** |
| 恢复 vsync，不限帧 | 13.66 | 12.0 | 14.9 | 3.0 ~ 3.6，跨 12.5 线 |
| 恢复 vsync，限 60 | 17.07 | 14.6 | 20.9 | 3.5 ~ 5.0 |

两条实测结论：
1. **在解码 vsync 的状态下限帧会明显更糟**：rAF 是 0.5ms 连发/13ms 工作时序，限 60 变成 3.4 拍与 7.7 拍交替 —— 与社区结论一致（Pixi 的 `maxFPS` 是「跳过 rAF」，跳哪一帧由系统定）。
2. 光是恢复 vsync 也还不够：工作量跨 12.5ms 这条线，出帧仍然 3/4 拍随机跳。

### 8.4 所以正确的目标是「落在单一拍上」，不是「更快」

- 4 拍 = 16.67ms（60fps）：工作量 12.83 / max 15.4，**余量约 1.3–3.9ms**，可达且稳。
- 3 拍 = 12.5ms（80fps）：需要工作量稳定 ≤ ~11.5ms，即再省 **≥1.5ms 且留余量**，当前不达标。
- 且**不能靠 `ticker.maxFPS` 实现**（8.3 已证伪），需要一个以 rAF 时间戳为锚的固定步进调度器：
  `next += 16.667`，只在 `ts >= next` 时推进，让相位钉在网格上，而不是跟随实际耗时漂移。

### 8.5 落地结果（当天完成）

结论：**出帧节奏改由引擎内的「网格锚定循环」驱动**（`src/stage/engine.js` 的 `frameLoop`），
配合两件事才真正稳下来：

1. **恢复 vsync**（删掉 `disable-gpu-vsync` / `disable-frame-rate-limit`，只留 `STAGE_NO_VSYNC=1` 做排查口）；
2. **每帧提前一拍开工**（`leadMs = 一个刷新周期`）。这一条是关键：
   单帧耗时 12～14ms、槽长 16.67ms，等「正好到点」才动手时提交常常赶不上这一拍，
   浏览器就把 BeginFrame 推后 → 表现为每隔几帧掉成 2 倍间隔（实测 60fps 档只有 ~51fps、约 17% 掉帧）。
   提前 4.17ms 开工后提交余量够了，实测变成 59～60fps、几乎每帧都精确 4 拍。

最终实测（打包版，457×837 窗口，240Hz）：

| 档位 | 目标 | 实测 | 间隔分布 |
| --- | --- | --- | --- |
| 正常 | 60 | **60.0 ~ 60.5 fps** | 4 拍 ×239/240，p90 16.8ms |
| 子窗口打开时 | 48 | 48.0 fps | 5 拍 ×191/191 |
| 调试档 | 30 | 30.0 fps | 8 拍 ×119/119 |

同时做的两件配套改动：

- **帧率不再是设置**：`settings.fps` 从默认值、设置页、托盘里全部移除；固定 60（子窗口打开时 30）。
  老配置里残留的 `fps` 字段读进来会被忽略。
- **resize 与出帧同拍**：窗口尺寸变化只记「待办」，真正 `renderer.resize` 放进下一帧的出帧钩子里，
  一帧最多重排一次（以前每个 resize 事件都会立刻重建画布）。实测改尺寸后 120ms 内画布即跟上，
  且节奏仍是 4 拍。

`__probe.frameInfo()` 可随时读出：`periodMs / beats / stepMs / leadMs / costMs / ticks`。

### 8.6 仍可继续的（没做）

- [ ] `?noaa=1` 的 antialias A/B：实测关掉只省 0.3～0.5ms（13.0 → 13.3 上下），**不是瓶颈**，可不再试。
- [ ] 降内部渲染分辨率：实测 75% 只省 0.35ms，说明单帧成本在 CPU 侧的**逐 drawable 提交**，
      不在填充率——想再快得减 draw call，不是改分辨率。
- [ ] 若要 80fps（3 拍）：需要稳定 ≤11.5ms，还差 ~1.5ms，且必须留余量，当前不做。
- [ ] 不碰：GL 状态缓存、网格缓存、掩码预处理（前三项已回滚/已证伪，第四项本技术栈不可达）。
